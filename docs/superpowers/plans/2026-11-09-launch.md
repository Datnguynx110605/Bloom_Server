# Launch Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the launch service of `doc/low-level-design/01-launch.md` (API and worker as one app): fair waiting room, admission passes, allocation holds and settlement, with every test case L-01 … L-16, L-19 … L-22 and every §8 edge case covered.

**Architecture:** One ASP.NET Core app `Bloom.Launch`; `Launch:Mode` = `api` | `worker` (HLD-ADR-014). API mode hosts a transcoded `LaunchCustomer` (`GetLaunch`, `JoinWaitingRoom`, `GetWaitingRoomStatus`), a transcoded `LaunchAdmin` (11 methods), the existing plain-gRPC `LaunchInternal` (`HoldAllocation`) and the shared DLQ admin. Worker mode runs the `Bloom.Shared` outbox relay, consumer host and retention purger, plus `AdmissionWorker` (1 s), `StageScheduler` (5 s) and `StuckHoldMonitor` (1 min). PostgreSQL holds the counters and is the only judge of LR-01 / LR-02 (guarded single-statement updates + `CHECK`). Redis holds the queue, the pass records and a 5 s state cache; the customer API reads only Redis (LR-04).

**Tech Stack:** .NET 10, ASP.NET Core gRPC + JSON transcoding, EF Core 10 + Npgsql, StackExchange.Redis, Bloom.Shared, xUnit v3, Testcontainers (PostgreSQL, RabbitMQ, Redis), Microsoft.Extensions.TimeProvider.Testing.

**Spec:** `docs/superpowers/specs/2026-11-09-launch-design.md` (approved; cited "spec §x"). Design source: `doc/low-level-design/01-launch.md` (cited "§x"). Where the spec is silent, 01-launch decides. Where both are silent, the owner items and rulings below decide.

## Owner items (plan approved 2026-11-09)

Items 1–3 approved as recommended with the plan. Each is visible outside launch and covered by neither 01-launch nor the spec. The recommendation is what the tasks build.

1. **Status after the room closes.** §6.3 reads the queue rank before the room state, and the spec deletes the queue at close only "best effort". If that delete fails, or a join slips in on a stale cache, a queued customer would see `queued` in a closed room (L-12 says `closed`). **Recommendation:** status checks the pass, then `closed`, then the rank: a live pass still shows `admitted` (spec §7), and a closed room never shows `queued`. Doc edit 7. (Task 4)
2. **Redis unreachable.** §8 accepts lost joins on failover but doesn't say what the API answers. **Recommendation:** `GetLaunch`, `JoinWaitingRoom` and `GetWaitingRoomStatus` return plain `UNAVAILABLE` (no `bloom` reason, as order's upstream failures) and never fall back to Postgres (LR-04). `HoldAllocation` doesn't need Redis (HMAC, §8) and succeeds; its after-commit cleanup logs a warning. Doc edit 8. (Tasks 4, 7)
3. **`PublishLaunch` rule failures.** §6.7 lists "≥ 1 SKU; every product has a limit; `launch_time > now()`" and spec §4 adds "≥ 1 SKU per product", but no reason. **Recommendation:** `VALIDATION_FAILED`, field `skus` (no SKU, or a product without one; the message names the product) or `launch_time` (`<= now()`). Doc edit 9. (Task 6)

## Global Constraints

- Build settings from `Directory.Build.props` (net10.0, Nullable, ImplicitUsings, `TreatWarningsAsErrors`). Central versions in `Directory.Packages.props`. **No new NuGet packages** (spec §5).
- No method, message, field, error reason, metric or route that 01-launch, the spec or the owner items don't list (AGENTS.md §1). No health endpoints. Never touch `doc/`, `Bloom.Shared`, the gateway, other services, `Bloom.Launch.Contracts` or any `.Contracts` project, Dockerfiles, Compose or manifests (spec §3).
- The anti-goals of spec §3 are hard rules: never `sold + held > allocation` or `> purchase_limit` (LR-01, LR-02); a pass enables one successful hold and a failed hold never uses it up (LR-03); no customer popped without a pass record; status never queries Postgres on the request path (LR-04); launch never releases a hold on its own (LR-07); a draft is never visible through `GetLaunch`; `account_id` only from `x-bloom-user-id`; a pass key never in a log, response or event.
- Clocks (spec §7): the app `TimeProvider` for join scores, the 15-min opening and the derived room state. Database `now()` for every check and every stored timestamp inside a transaction (R6).
- Every gRPC error has the `BloomErrors.Create` shape (ErrorInfo domain `bloom`). Reasons and statuses come from Task 1's table only.
- JSON field names are proto lowerCamel; `int64` fields are JSON strings.
- Docker via Colima: never run `colima`. If the daemon is unreachable, stop and report. Never `dotnet run`. Test containers must be gone after the run. **No test reaches the internet:** catalog is `FakeCatalog` on `127.0.0.1`.
- Every test case L-01 … L-16, L-19 … L-22 has at least one test whose method name starts with its ID: `L01_…`. Test names below are binding; the listed assertions are the minimum.
- Test command: `dotnet test --project src/Launch/Bloom.Launch.Tests`, narrowed with `--filter-class '*<Class>'`.

## Review Focus

1. **Order retries `HoldAllocation` while the first call is still running** (same `order_id`, same pass, after order's 2 s deadline). Both calls return the same `hold_id`; one `holds` row, one `consumed_passes` row, counters moved once; never `PASS_ALREADY_USED` (R12). Test in Task 7.
2. **Garbage pass tokens**: `""`, `"abc"`, `"a.b"`, non-base64url parts, a payload that isn't JSON, JSON missing `exp` or with `exp` a string, an unknown `kid`. Every one is `PASS_INVALID`, never `INTERNAL`. Tests in Tasks 3 and 7.
3. **Huge quantities**: one line of `int.MaxValue`, or two SKUs of one product at `2^30` each. `LIMIT_EXCEEDED` with the right `remaining` (or `SOLD_OUT`), never an `integer out of range` error; counters unchanged (R11). Test in Task 7.
4. **`order.paid.v1` and the release command for one held hold, handled at the same time.** Either order ends with the hold `released`, SKU and limit `held = sold = 0`, and one `launch.hold-released.v1`. Test in Task 9.
5. **Redis unreachable** (owner item 2): a host pointed at a dead Redis port returns `UNAVAILABLE` for join and status within 2 s, and `HoldAllocation` still succeeds. Tests in Tasks 4 and 7.

## Rulings in this plan (builder's calls the spec left open)

- **R1** Tests run the app on `TestServer` (as payment R1). gRPC goes through `GrpcChannel.ForAddress(base, new() { HttpHandler = server.CreateHandler() })`; transcoded routes through `Http`. Tests emulate the gateway with `x-bloom-user-id/type/role`.
- **R2** The app never migrates at startup; tests migrate. `DesignTimeFactory` uses env `Launch__Database` if set, else `Host=design-time;Database=launch`.
- **R3** `TryAddSingleton(TimeProvider.System)`; tests register `FakeTimeProvider` first. `IConnectionMultiplexer` is a singleton with `AbortOnConnectFail = false` (as identity), so the app builds and serves without Redis.
- **R4** Config section `Launch`: `Mode`, `Database`, `RabbitMq`, `Redis`, `Catalog` (absolute URL), `PassKeys` (list of `{ Kid, Key }`), `CurrentPassKid`, `AdmissionCeiling` (default 200, ≥ 1). Both modes need every key. Startup fails, naming the key, when a key is missing or invalid: unknown mode, relative `Catalog`, an empty or duplicate `Kid`, a `Key` that isn't base64 or is under 32 bytes, `CurrentPassKid` not listed. The message never contains a key value. `appsettings.json`: `Mode=api`, `RabbitMq=amqp://rabbitmq:5672`, `Catalog=http://catalog:8080`, `AdmissionCeiling=200`; the rest come from the deployment.
- **R5** `BloomOptions.ServiceName = "launch"`; telemetry `launch-api` / `launch-worker`; meter `Bloom.Launch`. Launch sends no commands (no `SendsCommandsTo`). Both modes register both consumers (the DLQ admin needs them): `order-paid` → `launch.order-paid` (`ConsumerBinding.Event("order", OrderMessages.Paid)`), `release-allocation-hold` → `launch.release-allocation-hold` (`ConsumerBinding.Command(LaunchMessages.ReleaseAllocationHold)`). Only the worker calls `AddWorker()` and adds the three hosted services.
- **R6** Every timestamp written in a transaction (`created_at`, `updated_at`, `consumed_at`, `waiting_room_closed_at`) is the database's `now()`, read once with `LaunchDbContext.NowAsync` or written as `now()` in SQL. Pass `exp` compares with it in milliseconds.
- **R7** Roles (spec §6): `Caller.From(ctx)` (copy catalog's, with `TryFrom` unused and dropped). Join and status: `RequireCustomer()`. Admin: `RequireStaff("catalog_manager", "admin")`. `HoldAllocation`: `RequireCustomer()`. Missing `x-bloom-*` → `InvalidOperationException`. The role check runs first. `GetLaunch` has no check.
- **R8** Path ids: a `launch_id` that isn't a UUID is `NOT_FOUND` on `GetLaunch`, join and status (an unknown launch), and `VALIDATION_FAILED` field `launch_id` on admin methods (spec §7 "valid UUIDs").
- **R9** Admin writes run in one transaction: `SELECT … FROM launches WHERE id = @id FOR UPDATE` (absent → `NOT_FOUND`), then the `version` check (→ `ABORTED` / `CONCURRENCY_CONFLICT`, and `BloomMetrics.OptimisticConflict("launch")`), then the stage rule, then the change, `launches.version + 1`, `updated_at = now()`, the audit row and, when R10 says so, the stage-changed event. After commit: drop `wr:{L}:state` (best effort, warning on failure), set `allocation_available` for changed SKUs, and return the admin view. Lock order everywhere: `launches` → `holds` → `limit_usage` (product asc) → `launch_skus` (sku asc).
- **R10** `launch.stage-changed.v1` is built by one helper from the row, all its products and all its SKUs as they are in the transaction. Written by: `PublishLaunch`, both scheduler transitions, and from `announced` on by `AddLaunchProduct`, `AddLaunchSku`, `SetPurchaseLimit`, `SetReleaseDate` (spec §7). Never for a draft.
- **R11** Guarded statements compute in `bigint` (`held::bigint + sold + @n <= @limit`), and the hold sums quantities per product as `long`; a sum above `purchase_limit` fails `LIMIT_EXCEEDED` before any SQL.
- **R12** `HoldAllocation` step 4 uses `INSERT … ON CONFLICT (pass_id) DO NOTHING`. Zero rows → read `holds` by `order_id` again (the concurrent first call has committed by then) and apply step 2; only when there is still no hold → `PASS_ALREADY_USED`. A `23505` on `ux_holds_order_id` at step 7 → roll back and run once more from step 2. This is §8 "order retries after a timeout" under concurrency.
- **R13** Audit (spec §7): copy catalog's `Audit` (`IdentityMessages.StaffActionRecorded`, `StaffActionRecorded`). Target type `launch`, target id the launch id. Actions (06-identity §4.1's `launch.allocation-changed` style): `launch.created`, `launch.product-added`, `launch.sku-added`, `launch.allocation-changed`, `launch.purchase-limit-changed`, `launch.release-date-changed`, `launch.launch-time-changed`, `launch.admission-rate-changed`, `launch.published`. Details: `{before, after}` for changes (with `skuId` / `productId` when the target is one), the added row for adds, `{}` otherwise.
- **R14** Metric labels: `launch` and `sku` are ids in `D` format. `holds_total{result}` = `ok` (idempotent retries too) | `sold_out` | `limit_exceeded` | `pass_invalid` | `pass_expired` | `pass_already_used`; other rejections aren't counted (§10 lists no label for them). `admission_ticks_total{result}` = `admitted` (≥ 1 popped) | `skipped_lock` | `none`. `waiting_room_size` and `passes_outstanding` are set by the tick; `allocation_available` after holds, settlements and admin changes (after commit, from `RETURNING allocation - held - sold`); `stuck_holds` by the monitor. Gauges are observable gauges over a `ConcurrentDictionary`.
- **R15** State cache (spec §7): JSON snapshot in `wr:{L}:state`, `EX 5`. A launch with no row is cached as a `missing` marker for 5 s too (a random id must not reach Postgres per request). Single flight per pod per launch: a `ConcurrentDictionary<Guid, Task<LaunchSnapshot?>>` entry removed when the load ends. Admin writes and scheduler transitions drop the key after commit; holds and settlements don't (the 5 s TTL is the bound, spec §7).
- **R16** Room cleanup (spec §7): after a close commits, `DEL wr:{L}:q wr:{L}:passes wr:{L}:state` (one call, same slot). Each admission-worker pass also retries it for launches closed within the last hour whose `q` or `passes` still exists (`EXISTS`). Pass keys `wr:{L}:pass:{A}` expire on their own.
- **R17** Ids are `Guid.CreateVersion7()`. Hold response lines and `hold_lines` are ordered by `sku_id`.
- **R18** Test isolation: one database per test host; one Redis for the run, isolated by fresh launch ids. Consumers are tested by invoking the handler in a scope and transaction like `ConsumerHost` (`Consume.Async`, as payment). Feature tests read events from the outbox table; `WorkerTests` publish `order.paid.v1` and the release command to the broker and read the three published events off it (spec §8). Worker jobs are driven by their `RunOnceAsync` / `TickLaunchAsync` methods; only `WorkerTests` start a worker host.
- **R19** The bare `GET`/`POST /api/admin/launches` relies on the existing `/api/admin/launches/{**rest}` route, by order's precedent (`GET /api/admin/coupons` behind `/api/admin/coupons/{**rest}`). No gateway test (the gateway is out of scope).
