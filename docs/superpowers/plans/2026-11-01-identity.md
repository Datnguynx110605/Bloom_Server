# Identity Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the identity service of `doc/low-level-design/06-identity.md` (API and worker deployments as one app), the `Bloom.Identity.Contracts` payload records, and `Bloom.Order.Contracts` (the `HasUnsettledOrders` proto).

**Architecture:** One ASP.NET Core app `Bloom.Identity`; `Identity:Mode` = `api` | `worker` (HLD-ADR-014). API mode hosts four gRPC services (one per LLD §3 component: `Auth`, `Account`, `Staff`, `Admin`) transcoded to JSON on the spec §6 paths, the JWKS endpoint and the shared DLQ admin. Worker mode runs the `Bloom.Shared` outbox relay, consumer host (audit consumer), retention purger, plus an hourly cleanup job. PostgreSQL through EF Core (`AddBloom<IdentityDbContext>`), Redis for counters / challenges, RabbitMQ only through `Bloom.Shared`.

**Tech Stack:** .NET 10, ASP.NET Core gRPC + JSON transcoding, EF Core 10 + Npgsql, ASP.NET Core Data Protection (EF key store), StackExchange.Redis, Microsoft.IdentityModel.JsonWebTokens, Sodium.Core (Argon2id), `System.Security.Cryptography` (AES-GCM, HMAC), Bloom.Shared, xUnit v3, Testcontainers (PostgreSQL, Redis, RabbitMQ), Microsoft.Extensions.TimeProvider.Testing.

**Spec:** `docs/superpowers/specs/2026-11-01-identity-design.md` (approved; cited "spec §x"). Design source: `doc/low-level-design/06-identity.md` (cited "§x"). Where the spec is silent, 06-identity decides; where both are silent, the rulings below decide.

## Review Focus

1. **Blocked, deactivated or Google-only account with the right password**: `INVALID_CREDENTIALS`, byte-identical body to an unknown email, exactly one Argon2id verification (no existence leak by timing, ID-05). Test in Task 6.
2. **Password reset rate limit for unknown vs known emails**: the same sequence of statuses for six requests in an hour (the limit must not reveal an account, ID-05). Test in Task 7.
3. **Two concurrent `Refresh` calls with one cookie**: exactly one 200, the other `REFRESH_INVALID`, all of the account's tokens end `revoked`, one `tokens-revoked` row (§7). Test in Task 4.
4. **Email case and whitespace**: sign up with `" Ann@Example.COM "`, sign in with `ann@example.com`; `StartSignUp` / `InviteStaff` with another casing of an existing email → `EMAIL_ALREADY_REGISTERED` / `EMAIL_TAKEN`. Tests in Tasks 5, 6, 11.
5. **Unicode passwords**: 12 emoji accepted and 11 rejected (scalar count, not UTF-16), a full-width (NFKC-equivalent) form of the password signs in, `PASSWORD1234` rejected. Tests in Tasks 3 and 6.

## Rulings in this plan (builder's calls the spec left open)

- **I1** Identity tests run the app on `TestServer` (`Microsoft.AspNetCore.TestHost`, pinned). Fake Google JWKS and fake order server run on Kestrel `127.0.0.1:0` (order: `Protocols = Http2`, h2c). Tests read `Set-Cookie` and send `Cookie` themselves. Tests emulate the gateway by setting `x-bloom-user-id/type/role/auth-time`.
- **I2** The app never migrates at startup (deployment's job, out of scope). Test infra runs `Database.MigrateAsync()` on a fresh database per host. An `IDesignTimeDbContextFactory` serves `dotnet ef`.
- **I3** `TryAddSingleton(TimeProvider.System)`; tests register `FakeTimeProvider` first. Redis TTLs are real time; tests that cross them delete or inspect keys.
- **I4** Registration token payload `{email, verifiedAt}` (§4.3). Rejected when unprotect fails, or `now − verifiedAt > 30 min` on the `TimeProvider`; Data Protection's own 30-min expiry stays as a system-clock backstop.
- **I5** Data Protection keys are always protected with the certificate in `Identity:DataProtection:Certificate` (base64 PKCS#12, no password); tests generate a self-signed one. One code path instead of spec §7's "unprotected ring in tests". Application name `bloom-identity`.
- **I6** Config section `Identity`: `Mode`, `Database`, `Redis`, `RabbitMq`, `SigningKeys` (list of `{Kid, PrivateKeyPem}`), `ActiveKeyId`, `CodePepper`, `CodeEncryptionKey`, `TotpKey` (base64, exactly 32 bytes each), `DataProtection:Certificate`, `Google:ClientId`, `Google:JwksUrl` (default `https://www.googleapis.com/oauth2/v3/certs`), `InviteBaseUrl`, `OrderUrl`. Missing or invalid → throw at build naming the key. Worker mode needs only `Mode`, `Database`, `RabbitMq`. `appsettings.json` holds placeholders for non-secrets only (`Mode=api`, `Redis=identity-redis:6379`, `RabbitMq=amqp://rabbitmq:5672`, `OrderUrl=http://order:8080`, `InviteBaseUrl=https://bloom.example/staff/invitation`, Google JWKS default).
- **I7** `BloomOptions.ServiceName = "identity"`; telemetry names `identity-api` / `identity-worker`; meter `Bloom.Identity`.
- **I8** Both modes call `AddConsumer<AuditConsumer>("audit", …)` (the DLQ catalog needs it, see `MapBloomDeadLetterAdmin`); only the worker calls `AddWorker()`.
- **I9** Access token claims exactly `iss, aud, sub, typ, role` (staff only)`, auth_time, iat, exp, jti, sid`; no `nbf` (`SetDefaultTimesOnTokenCreation = false`). Header `alg=ES256`, `kid`, `typ=JWT`. 15 min. `jti` = new GUID.
- **I10** Cookie `bloom_rt`: `Secure; HttpOnly; SameSite=Strict; Path=/auth/refresh; Expires=<token expires_at>`. Clearing = same attributes, expired. Only `SignOut` clears it (spec §4).
- **I11** Refresh order: lookup by hash `FOR UPDATE` → missing or `expires_at ≤ now` → `REFRESH_INVALID` (no reuse handling) → `rotated`/`revoked` → reuse (`revoke_all`, trigger `refresh_reuse`, commit, then `REFRESH_INVALID`) → account not `active` → this token `revoked`, `REFRESH_INVALID` → rotate. `Cache-Control: no-store` on every Refresh response, errors included.
- **I12** Counters: `signin:fail` `INCR` (+`EXPIRE 900` when it returns 1); reaching 5 sets `signin:block` `EX 900` and deletes `signin:fail`; a correct password deletes `signin:fail`. `mfa:fail` / `mfa:block` the same. A blocked account still runs one dummy verification before answering.
- **I13** MFA challenge: id = 256-bit opaque token; Redis hash `mfa:challenge:{id}` `{accountId, attempts}`, `EX 300`; 5 attempts per challenge then deleted; success deletes it.
- **I14** Code limits: `SET code:cooldown:{email}:{purpose} 1 NX EX 60` fails → `CODE_RATE_LIMITED`; then `INCR code:hourly:…` (+`EXPIRE 3600` on 1) > 5 → `CODE_RATE_LIMITED`. `RequestPasswordReset` applies them **before** the account lookup, so unknown emails behave the same (ID-05). Code = `RandomNumberGenerator.GetInt32(0, 1_000_000)`, 6 digits zero-padded. Issuing marks previous unconsumed codes of the same (email, purpose) consumed.
- **I15** Code verify: latest unconsumed row for (target_email, purpose) — for `change_email`, (account_id, purpose). `attempts ≥ 5`, expired, or no row → `CODE_INVALID`; a mismatch increments `attempts`, commits, then `CODE_INVALID`. Success sets `consumed_at`.
- **I16** `ResetPassword`: password policy first (no attempt spent), then code. Unknown or non-`active` accounts: nothing sent on request, `CODE_INVALID` on reset. Staff may reset (TOTP still required to sign in).
- **I17** `ChangePassword`: re-auth → new password policy → current password check (null hash = mismatch; counts toward lockout; blocked → `INVALID_CREDENTIALS`).
- **I18** Re-auth (§6.7) on `ChangeEmail`, `ConfirmEmailChange`, `ChangePassword`, `UnlinkGoogle`, `DeleteAccount` (§5.1 marks both email methods). Boundary: `now − auth_time ≤ 300 s` passes.
- **I19** Google: new customer's name = `name` claim, else the email's local part, truncated to 100 scalars. `LinkGoogle` replaces the caller's existing `google_sub`; a sub on another account → `GOOGLE_ALREADY_LINKED`.
- **I20** Message emails: `verification-code` and `staff-invited` carry the normalized email; `customer-registered` and `contact-changed` carry `email_display`. `expiresAt` is ISO-8601 UTC.
- **I21** Response shapes: token-issuing methods return `{accessToken}` (+cookie). `GetMe` = `accountId, type, email, name, role, googleLinked, hasPassword`. `ListStaff` = every staff account, unpaged: `accountId, email, name, role, status, mfaEnrolled, createdAt, lastSignInAt`.
- **I22** `QueryAuditLog`: optional ANDed filters `from` (incl.), `to` (excl.), `actorId`, `service`, `action`, `targetType`, `targetId`; newest first by `(occurred_at, id)` desc; `pageSize` 0 → 50, 1–200 ok, else `VALIDATION_FAILED`; `pageToken` = base64url of the last row's key; malformed → `VALIDATION_FAILED`.
- **I23** Address: `recipient`, `line1`, `city` 1–100 chars; `label`, `line2` 0–100; `state` ∈ 50 states + `DC` (US only, PD-ADR-002); `zip` `^\d{5}(-\d{4})?$`; `phone` optional, E.164 `^\+[1-9]\d{1,14}$`. `isDefault = true` clears the others. New version = 1.
- **I24** Email: trim; total ≤ 254, local part 1–64; must satisfy `MailAddress.TryCreate` with `Address` equal to the trimmed input; normalized = `ToLowerInvariant()`. Name: trimmed, 1–100 Unicode scalars.
- **I25** Staff no-ops (deactivate deactivated, reactivate active, same role) → success, nothing written. `LAST_ADMIN` covers demote and deactivate only (§5.3), logged as a warning (§10 lists no metric).
- **I26** Identity audit rows: `target_type = staff_account`, `target_id` = account id, or the normalized email for `identity.staff-invited` (no account yet). `details`: invite `{role}`, role change `{before, after}`, status `{before, after}`, MFA reset `{}`.
- **I27** Re-enrol accept: invitation role ignored; account must be `active` else `INVALID_CREDENTIALS`; wrong first TOTP → `MFA_INVALID` and the invitation stays usable (also for new staff).
- **I28** Metric labels: `signins_total{type=customer|staff|unknown, method=password|google|mfa, result=success|mfa_required|invalid|not_allowed}`; `signin_seconds` per `SignIn` call; `refresh_total{result=rotated|reuse|invalid}`; `revocations_total{trigger=sign_out|sign_out_everywhere|password_change|password_reset|refresh_reuse|account_deleted|staff_deactivated|staff_role_changed|staff_mfa_reset}`; `codes_sent_total` / `code_failures_total{purpose}`; `account_deletions_total{result=deleted|unsettled_orders|order_unavailable}`; `audit_entries_total{service}` per inserted row (consumer or own).
- **I29** `IdentityDbContext.SaveChangesAsync` bumps `Version` and sets `UpdatedAt` for modified `Account` entries; account changes go through tracked entities. RPCs that mix `ExecuteUpdate`/raw SQL with tracked changes wrap everything in one explicit transaction.
- **I30** Deletion removes codes with `account_id = id` or `target_email` = the old normalized email.
- **I31** Missing trusted context on a `/api/me` or admin method → `InvalidOperationException` (as `DeadLetterAdminService` does; the gateway always sets it).
- **I32** `refresh_tokens.user_agent` = request `User-Agent`; `ip` = connection remote address.
- **I33** Display email: at sign-up, the registration token's `email` is the trimmed address given to `VerifySignUpCode` (account `email_display`); `email_normalized` is derived from it. On email change, codes store only the normalized target, so the new `email_display` = normalized. Staff accounts: display = normalized invitation email.
