# Payment Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the payment service of `doc/low-level-design/04-payment.md` (API and worker as one app) behind a hand-written Stripe client, with every test case P-01 … P-11 and every §8 edge case covered.

**Architecture:** One ASP.NET Core app `Bloom.Payment`; `Payment:Mode` = `api` | `worker` (HLD-ADR-014). API mode hosts the existing internal `PaymentInternal` (plain gRPC, `CreatePayment`), a transcoded `PaymentStaff` (`GetPayment`), the plain-HTTP `POST /webhooks/stripe` and the shared DLQ admin. Worker mode runs the `Bloom.Shared` outbox relay, consumer host and retention purger, plus `ProviderExecutor`, `Reconciler` and `NightlyJob`. Every Stripe call goes through `IPaymentProvider` (HLD-ADR-018), implemented by `StripeClient` (`HttpClient`, form-encoded requests). Every status change is a guarded single-statement update (00-reliability §7.5), and the webhook, the executor and the reconcilers share one `Transitions` class (§6.5).

**Tech Stack:** .NET 10, ASP.NET Core gRPC + JSON transcoding, EF Core 10 + Npgsql, Bloom.Shared, xUnit v3, Testcontainers (PostgreSQL, RabbitMQ), Microsoft.Extensions.TimeProvider.Testing.

**Spec:** `docs/superpowers/specs/2026-11-08-payment-design.md` (approved; cited "spec §x"). Design source: `doc/low-level-design/04-payment.md` (cited "§x"). Where the spec is silent, 04-payment decides. Where both are silent, the owner items and rulings below decide.

## Owner items (plan approved 2026-11-08)

Items 1–5 approved as recommended with the plan. Each is visible outside payment and covered by neither 04-payment nor the spec. The recommendation is what the tasks build.

1. **`CreatePayment` with another amount on a `creating` row.** Spec §7 checks the amount only on `open`, `succeeded`, `expired` and `canceled`. A stale `creating` row taken over with another amount would send Stripe a different body under the same key, and fail as `PROVIDER_UNAVAILABLE` on every retry. **Recommendation:** compare the amount first, for every existing row: a different amount → `PAYMENT_EXISTS_DIFFERENT_AMOUNT`. Doc edit 10. (Task 4)
2. **Lock after a known Stripe failure.** §6.1 says "the next call resumes", but a 60 s lock makes a quick retry get `PAYMENT_CREATE_IN_PROGRESS`. **Recommendation:** when the Stripe call fails or times out, the claimer sets `locked_until = now`, guarded on its own lock value, so the next call resumes at once. A crash still waits the 60 s (P-02). Doc edit 11. (Task 4)
3. **Webhook bodies.** **Recommendation:** a body over 256 KB → `413`. A body with a valid signature that is not a JSON object with a string `id`, a string `type` and an integer `created` → `400`, nothing stored, an error log, and `webhooks_total{type="unknown", result="error"}`. Doc edit 12. (Task 5)
4. **Cancel executor, session already complete.** Spec §7 says the executor "applies its state the way the reconciler does" and "a completed session waits for the `completed` transition". Leaving the payment `open` makes the executor call `expire` and `retrieve` again every 5 s until the webhook arrives. **Recommendation:** the executor applies the completed transition at once, with the reconciler's code (`succeeded`, `late = true`). A later webhook is a no-op. Doc edit 13. (Task 7)
5. **`failureReason` values in `payment.refund-failed.v1`.** **Recommendation:** Stripe's refund `failure_reason` when Stripe reports `failed` or `canceled` (the status itself when Stripe gives none). Stripe's error reason (R10) for a permanent `refunds.create` error. `provider_unavailable` after the 5th transient failure. Doc edit 14. (Task 6)

## Global Constraints

- Build settings from `Directory.Build.props` (net10.0, Nullable, ImplicitUsings, `TreatWarningsAsErrors`). Central versions in `Directory.Packages.props`. **No new NuGet packages** (spec §4).
- No method, message, field, error reason, metric or route that 04-payment, the spec or the owner items don't list (AGENTS.md §1). No health endpoints. Never touch `doc/`, `Bloom.Shared`, order, fulfillment, identity, the gateway, the message records in `Bloom.Payment.Contracts`, Dockerfiles, Compose or manifests (spec §3).
- The anti-goals of spec §3 are hard rules: at most one Stripe session per order and one successful charge (PR-01); `Idempotency-Key` on every `checkout.sessions.create` and `refunds.create` (PR-02); no webhook processed without a valid signature, none applied twice per event ID (PR-03); `refunded_cents ≤ amount_cents` under concurrency (PR-04); nothing that identifies the customer sent to Stripe or stored (PR-05); one `refund-completed` **or** one `refund-failed` per refund, never both, never twice.
- Idempotency keys exactly: `bloom:payment.create:<order_id>` and `bloom:refund:<refundId>` (UUIDs in `D` format).
- Business times come from the injected `TimeProvider`. SQL takes timestamps as parameters, never `now()`.
- Every gRPC error has the `BloomErrors.Create` shape (ErrorInfo domain `bloom`). Reasons and statuses come from Task 1's table only.
- JSON field names are proto lowerCamel; `int64` fields are JSON strings.
- Docker via Colima: never run `colima`. If the daemon is unreachable, stop and report. Never `dotnet run`. Test containers must be gone after the run. **No test reaches the internet:** the Stripe base URL in tests is the fake's, and `FakeStripe` fails any request it doesn't serve.
- Every test case P-01 … P-11 has at least one test whose method name starts with its ID: `P01_…`. Test names below are binding; the listed assertions are the minimum.
- Test command: `dotnet test --project src/Payment/Bloom.Payment.Tests`, narrowed with `--filter-class '*<Class>'`.

## Review Focus

1. **Concurrent refunds over the amount.** Amount 1000; five refund commands of 300 handled in parallel. Exactly three are accepted, two dead-letter, `refunded_cents = 900`, and Stripe gets three refunds. Test in Task 6.
2. **Executor and webhook settle the same refund at once.** `refunds.create` answers `succeeded` while `refund.updated` (`succeeded`) for the same refund arrives. One `refund-completed`, refund `succeeded`, no error log. Test in Task 6.
3. **Immediate retry after a Stripe timeout.** The fake stores the session, then answers after the 4 s timeout. The next `CreatePayment` (within 60 s) resumes, the fake sees the identical body under the same key (a changed body fails with `idempotency_error`), and the session is the first one. Test in Task 4.
4. **Same event delivered twice in parallel.** Two concurrent POSTs of one `checkout.session.completed`: one `200 processed`, one `200 duplicate`, one `payment.succeeded.v1`. Test in Task 5.
5. **Webhook and reconciler apply the same completion.** The 5-min reconciler and a late `completed` webhook run on one payment in parallel. One `payment.succeeded.v1`, one fix counted at most. Test in Task 8.

## Rulings in this plan (builder's calls the spec left open)

- **R1** Tests run the app on `TestServer` (as order R1). gRPC goes through `GrpcChannel.ForAddress(base, new() { HttpHandler = server.CreateHandler() })`. Tests emulate the gateway with `x-bloom-user-id/type/role`.
- **R2** The app never migrates at startup; tests migrate. `DesignTimeFactory` uses env `Payment__Database` if set, else `Host=design-time;Database=payment`.
- **R3** `TryAddSingleton(TimeProvider.System)`; tests register `FakeTimeProvider` first.
- **R4** Config section `Payment`: `Mode`, `Database`, `RabbitMq`, `StorefrontBaseUrl` (absolute URL), `Stripe:ApiKey`, `Stripe:WebhookSecret`, `Stripe:BaseUrl` (absolute URL). Both modes need every key. A missing or invalid key throws at build, naming the key. `appsettings.json`: `Mode=api`, `RabbitMq=amqp://rabbitmq:5672`, `Stripe:BaseUrl=https://api.stripe.com/`. The secrets and `StorefrontBaseUrl` come from the deployment.
- **R5** `BloomOptions.ServiceName = "payment"`; telemetry `payment-api` / `payment-worker`; meter `Bloom.Payment`. Payment sends no commands (no `SendsCommandsTo`).
- **R6** Both modes register both consumers (the DLQ admin needs the catalog): handler `refund-payment` → queue `payment.refund-payment`, `cancel-payment` → `payment.cancel-payment` (§5.2), each bound with `ConsumerBinding.Command`. Only the worker calls `AddWorker()` and adds `ProviderExecutor`, `Reconciler` and `NightlyJob`.
- **R7** Roles: `GetPayment` needs `x-bloom-user-type = staff` and role `support` or `admin`. Refusal → `PERMISSION_DENIED` / `ROLE_NOT_ALLOWED`. Missing `x-bloom-*` → `InvalidOperationException`. The role check runs before validation. `CreatePayment` has no role check (only order can reach it, §9; as order's `HasUnsettledOrders`).
- **R8** Guarded updates (spec §7): one conditional `UPDATE … SET …, version = version + 1, updated_at = @now WHERE id = @id AND status = ANY(@from) … RETURNING …`, with an affected-row check. Lock order is always `refunds` → `payments`. `locked_until` is set to null whenever a payment leaves `creating`.
- **R9** Validation (`VALIDATION_FAILED`, `metadata["field"]` = proto field name): `order_id`, `account_id` UUIDs; `amount_cents > 0`; `display_lines` non-empty; each `display_lines.amount_cents ≥ 0`; Σ line amounts = `amount_cents` (field `display_lines`) (spec §6). `GetPayment.order_id` a UUID.
- **R10** Stripe client (spec §7): bearer API key, `Stripe-Version: 2024-06-20`, form-encoded bodies built as an ordered list of pairs (`FormUrlEncodedContent`), responses read with `System.Text.Json`. `HttpClient.Timeout` 10 s; `CreateSessionAsync` also cancels after 4 s. 5xx, 429, timeouts, network and unreadable responses → `ProviderException { Transient = true }`; other 4xx → `Transient = false`, `Reason` = `error.code` ?? `error.type` ?? `http_<status>`. `order_number` is shown on Stripe's page as `custom_text[submit][message] = "Order <order_number>"`.
- **R11** `FakeStripe` is an `HttpMessageHandler` behind the real `StripeClient` (as fulfillment's `FakeShippo`), with the test clock. It serves only the eight endpoints of Task 3 and answers `404` + a failed assertion record to anything else.
- **R12** `ProviderExecutor` (`PeriodicTimer(5 s)`): each tick handles up to 50 items. Each item is one transaction that locks its row `FOR UPDATE SKIP LOCKED` across the Stripe call (fulfillment's `LabelWorker` pattern), so one failure never rolls back another. Refunds first (`pending`, `next_attempt_at <= now`, oldest first), then cancellations (`open`, `cancel_requested`, `session_expires_at > now`); a cancellation is tried at most once per tick.
- **R13** `Reconciler` (`PeriodicTimer(5 min)`) and `NightlyJob` (waits for `NextRun(now)`, the next 02:00 UTC). A Stripe error on one record is logged as a warning and skipped. The nightly job also runs the `provider_events` purge (spec §7, daily), in its own `try`. Nightly Bloom-side days: a payment by `succeeded_at`, a refund by `updated_at` of the `succeeded` row (a final row is never written again). A Bloom payment missing from Stripe's list is fetched with `checkout.sessions.retrieve(stripe_session_id)`; a match is `complete`, `paid`, the same intent and `amount_total = amount_cents`. A Bloom refund missing from the list is fetched with `refunds.retrieve`; a match is `succeeded` with the same amount. A failed fetch counts as a mismatch (reported, never corrected). Stripe-side items are looked up in Bloom by ID with no date limit. Only Stripe refunds with `status = succeeded` are compared.
- **R14** Metric labels: `payments_created_total{result}` = `created` | `existing` | `in_progress` | `different_amount` | `provider_unavailable`; `refunds_total{status}` = `submitted` | `succeeded` | `failed` (once per transition into that status); `webhooks_total{type}` = the event's `type`, `unknown` before the body is parsed; `reconcile_fixes_total{kind}` = `payment_succeeded` | `payment_expired` | `refund_succeeded` | `refund_failed`. `reconcile_mismatches` and `disputes_open` are gauges; the `Reconciler` pass sets `disputes_open`.
- **R15** Ids are `Guid.CreateVersion7()`. `succeededAt` (row and event) is the payment service's clock when the transition is applied.
- **R16** Test isolation: one database per test host. Consumers are tested by invoking the handler in a scope and transaction like `ConsumerHost` (`Consume.Async`, as order). Only `WorkerTests` start a worker host. The executor and the jobs are driven by their `Run…Async` methods.
