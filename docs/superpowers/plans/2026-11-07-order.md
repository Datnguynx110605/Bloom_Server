# Order Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the order service of `doc/low-level-design/03-order.md` (API and worker as one app), the launch and payment contracts it needs, and a multi-step form of the shared idempotency guard.

**Architecture:** One ASP.NET Core app `Bloom.Order`; `Order:Mode` = `api` | `worker` (HLD-ADR-014). API mode hosts four transcoded gRPC services, one per LLD §3 API component (`OrderCart`, `OrderCheckout`, `OrderCustomer`, `OrderStaff`), the existing internal `OrderInternal` (plain gRPC) and the shared DLQ admin. Worker mode runs the `Bloom.Shared` outbox relay, consumer host, retention purger, the two sweeps and a monitor. PostgreSQL through EF Core (`AddBloom<OrderDbContext>`). Every status change is a guarded single-statement update with its history row in the same transaction (00-reliability §7.5). `StartCheckout` runs in the new `IdempotencyGuard.ExecuteMultiStepAsync` (spec §4).

**Tech Stack:** .NET 10, ASP.NET Core gRPC + JSON transcoding, EF Core 10 + Npgsql, Bloom.Shared, xUnit v3, Testcontainers (PostgreSQL, RabbitMQ), Microsoft.Extensions.TimeProvider.Testing.

**Spec:** `docs/superpowers/specs/2026-11-07-order-design.md` (approved; cited "spec §x"). Design source: `doc/low-level-design/03-order.md` (cited "§x"). Where the spec is silent, 03-order decides. Where both are silent, the owner items and rulings below decide.

## Owner items (plan approved 2026-11-07)

Items 1–6 approved as recommended with the plan.

1. **Resumed checkout whose order is already cancelled.** A retry after the key was released, or after a stale lock, can find its order cancelled by a sweep, with no outcome stored on the key. **Recommendation:** new reason `CHECKOUT_CLOSED` (`FAILED_PRECONDITION`, "This checkout was cancelled; start a new one."), stored on the key. The same reason is used when Tx 2 finds the order no longer `creating`. Proposed doc edit 10. (Task 8)
2. **Hold refused on a resumed order.** An earlier attempt's hold may exist, for example `RESERVATION_CONFLICT` because the cart changed, or `PASS_EXPIRED` because launch checks the pass before it looks up the existing hold. Cancelling with no release would orphan that hold (OR-02). **Recommendation:** when the order came from `checkout_keys` (not inserted by this request), any hold rejection also sends the release command and opens a `checkout_compensation` saga. A new order keeps spec §7 (no saga). The rejection itself passes through. (Tasks 8, 9)
3. **`CreatePayment` failures.** **Recommendation:** every failure, including a `bloom` business status, becomes `UNAVAILABLE` (key released, order stays `pending_payment`) with an error log. The 15-min sweep expires the order if the client never retries (§6.2). (Task 8)
4. **Reason values on commands.** **Recommendation:** `RefundPaymentV1.Reason` from order = `cancellation` or `late_payment`. `ReleaseAllocationHoldV1.Reason` = the order's cancel reason (`checkout_failed`, `checkout_expired`, `customer`, `support`). (Tasks 8, 10, 12)
5. **Return decision with no accepted units.** **Recommendation:** status unchanged (rejected units don't count, §6.7). (Task 13)
6. **`order.cancelled.v1` on checkout failures.** §5.3 says "any cancellation". **Recommendation:** published for every cancellation, including `checkout_failed` at checkout and in the creating sweep. (Tasks 8, 10)

## Global Constraints

- Build settings from `Directory.Build.props` (net10.0, Nullable, ImplicitUsings, `TreatWarningsAsErrors`). Central versions in `Directory.Packages.props`. **No new packages** (spec §5).
- No method, message, field, error reason, metric or route that 03-order, the spec or the owner items don't list (AGENTS.md §1). No health endpoints. Never touch `doc/`, catalog, inventory, fulfillment, identity, the gateway, Dockerfiles, Compose or manifests. In `Bloom.Shared`, only the new guard form (spec §3).
- The anti-goals of spec §3 are hard rules: no hold before its order row is committed (OR-02); coupon uses never above a limit (OR-03); never `cancelled` and shipped (OR-04); line amounts sum exactly to the total and `refunded_cents ≤ paid_cents` (OR-05); a pre-order reaches `paid` only with `stock_allocated` and `launch_released` (OR-07); one `order.ready-to-fulfill.v1` per order; every status change has its history row, and every saga command has its saga row, in the same transaction.
- Every staff write publishes `StaffActionRecorded` in its transaction: `service = order`, `action = order.<method in kebab case>` (spec §7).
- Business times come from the injected `TimeProvider`. SQL takes timestamps as parameters, never `now()` (the guard's own SQL is excepted).
- Every error has the `BloomErrors.Create` shape (ErrorInfo domain `bloom`). Reasons and statuses come from Task 3's table only. Inventory's and launch's reasons pass through (§5.4).
- JSON field names are proto lowerCamel; `int64` fields are JSON strings.
- Docker via Colima: never run `colima`. If the daemon is unreachable, stop and report. Never `dotnet run`. Test containers must be gone after the run. No test reaches the internet.
- Every test case O-01 … O-21 has at least one test whose method name starts with its ID: `O01_…`. Test names below are binding; the listed assertions are the minimum.
- Test command: `dotnet test --project src/Order/Bloom.Order.Tests`, narrowed with `--filter-class '*<Class>'`. Shared: `dotnet test --project src/Shared/Bloom.Shared.Tests`.

## Review Focus

1. **Retry after a mid-checkout transient failure.** Hold OK, then `CreatePayment` `UNAVAILABLE`. A retry with the same key gets the same order and number, `ReserveStock` is called again with the same `order_id` and lines, one coupon use exists, and the payment URL comes back. Test in Task 8.
2. **Paid vs expired race.** `payment.succeeded` and the expiry sweep on the same order in parallel. Exactly one wins: either `paid`, or `cancelled` plus a late-payment refund. Never both, and never neither. Test in Task 10.
3. **Other customers' orders.** `GetOrder` / `CancelOrder` on another customer's order, or on a `creating` one, gives `NOT_FOUND` with the same body as an unknown id. Lists never show them. Test in Task 12.
4. **Cart changed during the checkout.** The customer adds an item and raises a quantity while paying. After `payment.succeeded`, only the bought quantities leave the cart. Test in Task 10.
5. **Release redelivered after a partial run.** `launch.stage-changed` (`released`) is processed again after some batches committed. Each order still gets one `ready-to-fulfill` or one `preorder-delayed`. Test in Task 11.

On 0 rows, re-read and map the error (stale version → `CONCURRENCY_CONFLICT`, else the method's status error). One helper does all of this: `Transitions.MoveAsync(Guid orderId, string[] from, string to, Actor actor, string? reason, long? version, Action<UpdateSettersBuilder<OrderRow>>? extra, CancellationToken) → Task<bool>`, with `record Actor(string Type /* customer | staff | system */, Guid? Id)` and `Actor.System`. A versioned call throws `CONCURRENCY_CONFLICT` on a stale version; otherwise 0 rows returns false and the caller maps the error.
- **R9** Validation (`VALIDATION_FAILED`, `metadata["field"]` = proto field name): ids are UUIDs; enum strings exactly as the LLD; paging `page` 0 → 1, `page_size` 0 → 50, otherwise 1–100. `ship_to` (§9) → `ADDRESS_INVALID` with `field`: `name` 1–100; `lines` 1–2 items of 1–100 chars; `city` 1–100; `state` a USPS code (50 states, `DC`, `AS`, `GU`, `MP`, `PR`, `VI`, `AA`, `AE`, `AP`); `zip` `^\d{5}(-\d{4})?$`; `phone` `^\+[1-9]\d{1,14}$`. Coupon code: trimmed, 3–32 chars of `[A-Za-z0-9-]`, else `VALIDATION_FAILED coupon_code` (or `code` on coupon writes). `SupportCancelOrder.reason` is 1–500 chars.
- **R10** Outgoing calls (`Domain/Upstreams.cs`): 5 s deadline each. `HoldAllocation` forwards the caller's `x-bloom-user-id/type/role` (spec §7). An `RpcException` carrying a `bloom` `ErrorInfo` from inventory or launch is rethrown with the same status and reason. Catalog `GetPricing` failure → `UNAVAILABLE` (§5.2). `CreatePayment` per owner item 3. `CancelPackTask` per spec §7. Everything else propagates unchanged.
- **R11** Ids are `Guid.CreateVersion7()`, refund ids too. Order number = `BLM-` + 8 chars from `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (`RandomNumberGenerator`). On `23505` on `ux_orders_number`, roll back to a savepoint and retry, inside Tx 1.
- **R12** Release commands and saga steps (spec §7, §6.6):

  | Case | Commands | `pending_steps` |
  |---|---|---|
  | regular, before payment (compensation, expiry) | `inventory.release-reservation.v1` | `{inventory_release}` |
  | launch, before payment | `launch.release-allocation-hold.v1` | `{launch_release}` |
  | regular, cancellation | release-reservation + refund | `{inventory_release, refund}` |
  | launch, cancellation | release-allocation-hold + release-reservation + refund | `{launch_release, inventory_release, refund}` |
  | late payment | refund (`total_cents`) | `{refund}` |

  Expiry also sends `payment.cancel-payment.v1` (no step). A completion event removes its step from every open saga of the order that has it (`array_remove`), and sets `completed_at` when the array is empty. Saga rows are inserted `ON CONFLICT DO NOTHING`; a conflict means the saga already ran, so no commands are sent.
- **R13** Coupon counters (§6.8): hold = the guarded update of §6.8 step 1, then usage upsert with guarded `+1`, then `coupon_uses (held)`. Release and restore subtract 1 from both counters, guarded by `uses_count > 0`. Use moves are guarded on the use's status: `held → consumed`, `held → released`, `consumed → restored`. `coupon_redemptions_total{result}`: `held`, `limit_reached`, `consumed`, `released`, `restored`.
- **R14** Sweeps (`Worker/Sweeps.cs`, `PeriodicTimer(10 s)`): `internal Task<int> RunCreatingAsync(CancellationToken)` and `RunExpiryAsync(CancellationToken)`. Each selects up to 100 orders past `deadline_at` with `FOR UPDATE SKIP LOCKED` and handles them in one transaction. Both loop until a batch returns fewer than 100 rows.
- **R15** Monitor (`Worker/OrderMonitor.cs`, every minute, `internal RunOnceAsync`): sets `orders_by_status`, `sagas_running{type}`, `sagas_stuck{type}` (open > 30 min), and logs one error when any saga is stuck (count and order ids).
- **R16** Test isolation: one database per test host. Consumers are tested by invoking the handler in a scope and transaction like `ConsumerHost` (`Consume.Async`, as fulfillment). Only `WorkerTests` start worker hosts. Sweeps and monitor are driven by their `Run…Async` methods.

### Task 1: Multi-step idempotency guard form (Bloom.Shared)

**Files:**
- Modify: `src/Shared/Bloom.Shared/Idempotency/IdempotencyGuard.cs`
- Test: `src/Shared/Bloom.Shared.Tests/IdempotencyTests.cs` (add a `MultiStep(...)` helper next to `TwoPhase(...)`)

**Interfaces:**
- Produces:
  - `public sealed record IdempotencyClaim(Guid UserId, string Key, bool Resumed);` `Resumed` is true when this request took over a stale key.
  - `public Task<TResponse> ExecuteMultiStepAsync<TRequest, TState, TResponse>(TRequest request, ServerCallContext context, Func<IdempotencyClaim, CancellationToken, Task<TState>> claimed, Func<IdempotencyClaim, TState, CancellationToken, Task<TResponse>> run)`, with the same generic constraints as `ExecuteWithProviderAsync`. Behaviour (spec §4):
    1. Tx 1: `ClaimAsync`. A replay returns at once and runs no hook. Otherwise run `claimed` (new or takeover), `SaveChangesAsync`, commit. An exception in the hook rolls back Tx 1 (the key stays unclaimed) and is rethrown.
    2. `run` may begin and commit its own transactions on the same `DbContext`.
    3. `run` returns, or throws an `RpcException` with a stored status: if `db.Database.CurrentTransaction` is open, the outcome is stored (`SaveChangesAsync` + fenced `CompleteAsync`) in **that** transaction and committed; otherwise in a new one. A rejection is rethrown after the commit.
    4. Any other exception: roll back an open transaction, `ReleaseAsync`, rethrow.
    5. Fence lost in step 3 (`CompleteAsync` already rolled back): claim again in a new transaction. Replay → return it. `IN_PROGRESS` → throw. Takeover → run `claimed` again in that transaction, commit, and go back to step 2.
  - The XML doc states the open-transaction rule, and that existing forms are unchanged.
